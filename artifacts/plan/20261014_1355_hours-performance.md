# 工时统计性能与界面响应性优化方案

## Summary

目标同时解决等待时间过长及加载期间假死。统计规则与完整性保护沿用已确认每日工时方案。推荐组合：Rust 后台请求线程 + Web Worker 计算 + 索引和缓存 + 按需渲染。本轮只完成源码诊断及计算基线，尚未实施业务改动。

已确认同步阻塞点：src-tauri/src/lib.rs 的 tapd_get 为同步 command，调用阻塞式 ureq 请求；Tauri 宏源码明确同步命令会阻塞主线程。HoursPage.vue 在 computed 中直接执行 calculateHours，同步占用 WebView JavaScript 线程。数据加载对每个未结束工作项分别查询累计工时，且页面卸载仅阻止旧响应提交，不停止旧请求队列。

## Implementation Plan

### 1. 先消除界面阻塞

- tapd_get 改为异步 command，将凭据读取和现有 ureq 阻塞 HTTP 放入 tauri::async_runtime::spawn_blocking；不能只加 async 后继续直接执行阻塞 HTTP。沿用已有请求代理、认证与错误契约。
- 采用 Web Worker 复用 TypeScript 独立统计函数；Worker 不直接调用依赖 window 的 Tauri 前端 API。网络经 Rust 后台执行，前端只协调任务；计算在 Worker 中运行。
- 计算结果存入 shallowRef，替换 computed 内同步计算。按数据版本向 Worker 传一次快照，规则重算传规则和版本，不重复复制大快照。
- 加入任务 ID、当前版本检查、Worker 错误处理；过期计算销毁或终止，组件卸载清理。计算结果、筛选和明细分开更新，保证旧结果不能覆盖新结果。
- 显示加载工作项、读取累计记录、计算、展示结果的阶段及已完成数量。相同范围刷新保留并标注旧数据，页面可滚动、切换与关闭。

### 2. 减少网络等待及重复请求

- 请求去重和短期内存缓存：以项目、账号上下文、成员集合、计算日和查询条件为键；日期窗口实际记录与完整累计分别缓存。手动刷新强制校验，配置成员／项目／凭据变化正确失效，旧缓存显示刷新时间。
- 多人工作项查询重叠按任务键去重，累计查询合并同一个在途请求；切换窗口复用同计算日有效的目录、工作项和累计数据。
- 增加查询取消标记：停止旧任务的待发分页、累计和重试；正在执行的阻塞 HTTP 使用原有超时并忽略结果，不将逻辑取消宣称为立即终止网络。
- 原生请求改为后台后仍保持全局并发限制，避免切换页面后旧队列叠加新队列。先沿用并发 3，不通过无限增加并发提速。
- 仅查看过去范围可先提供完整实际矩阵，任务元数据按需加载；未知元数据保持明确占位。预测数据仍需覆盖完整竞争区间，不能按当前展示月份截断。
- 不直接改为读取项目全部历史工时；大项目可能导致更大的数据量。项目批量累计或增量接口须先验证过滤、分页、删除和编辑语义，再决定是否替代逐任务读取。

### 3. 降低计算成本

- 一次建立 recordsByMember、tasksByMember、taskIssues、taskTotals、personalTotals 索引，避免每个成员重复扫描全部记录和工作项。
- 每个工作项预处理预估、终态、负责人份额和排序键一次；成员目标按日期缓存，日历覆盖／豁免和终态采用 Map／Set，避免内层重复 filter、some 和日期解析。
- 分配日期采用每个成员工作日日历和日期索引，去除“每个日期 × 每个任务 × dates.includes 日期扫描”；维护待分配活动任务和截止日任务，完成任务退出循环。
- 保持单有效日优先、截止日期／开始日期／唯一键顺序，以及截止日余量全部计入的规则。可用容量耗尽时，跳过可延后的任务，但必须处理当天截止任务。
- 每日贡献采用 Map 查找，代替数组 find。累计汇总保留全部相关记录；界面范围外只维护分配容量等必要数据，避免创建不展示的历史明细对象。
- Worker 保留索引和分配结果，筛选只裁剪展示结果；切换展示窗口不改变同日分配。目标／日历修改只重算，终态修改按需补齐累计记录。

### 4. 控制渲染成本

- 日期标题、格式化值、成员待安排数量与剩余汇总预计算，避免模板重复计算。
- 默认少量成员月视图保持简单表格。大成员数或长范围时，按测量结果加入行／列虚拟化，只渲染可见区域，保留固定成员列和日期表头。
- 明细只为当前选中成员日期生成／传递，长明细按需分页。Worker 回传结果避免一次携带大量范围外任务明细。

## Test Plan

- 所有统计回归保持通过：A～F 8/8/8、多负责人、累计、实际归属、豁免、逾期与完整性保护；优化前后完整输出对照。
- 使用相同数据和环境记录请求数量、获取时间、计算时间、Worker 传输时间、渲染时间及主线程长任务，分别报告冷启动、同范围刷新和切换窗口。
- 当前 Node 合成基线：6 成员、任务跨度 91 天、展示 31 天；300/1000/3000 任务及 1500/5000/15000 记录，三次暖运行分别约 26～28 / 81～83 / 256～257ms。该结果不等于桌面渲染或真实网络时间。
- 在同基准验证计算成本下降；重点验收获取和计算期间可滚动、切换和关闭应用，不再产生阻塞 HTTP 引起的长时间假死。交互响应目标 100ms 内，正常操作主线程单任务目标小于 50ms，以桌面实测确认。
- 验证 Worker 失败、取消、重复刷新、旧响应、规则修改及凭据变化。部分失败不能产生确定不足结论。
- 类型检查、自动测试、Rust 检查、macOS 发布构建及真实 TAPD 桌面性能验收；不以仅 Node 基准代替桌面验收。

## Assumptions

- 首轮采用后台线程，不新增独立子进程，避免进程启动、IPC 与跨平台分发成本；若测量发现内存隔离或 Worker 平台问题，再评估原生计算或独立进程。
- 增量接口和工时批量筛选尚未验证，不能直接依赖；缓存必须处理已填报记录编辑与删除。
- 优化目标包括响应性和总耗时；线程迁移解决阻塞，算法与请求优化负责减少实际等待。
