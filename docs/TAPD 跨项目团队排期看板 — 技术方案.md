# TAPD 跨项目团队排期看板 — 技术方案

* 文档版本：v1.0
* 项目类型：跨平台桌面应用
* 目标用户：需要同时管理多个 TAPD 项目及团队成员工作安排的研发管理人员
* 首版原则：只读、跨项目聚合、按成员分组、按日展示、可筛选、可追溯至 TAPD

---

## 1. 项目背景与目标

### 1.1 业务背景

团队同时承接约 10 个项目，每位成员可能同时参与多个项目。

TAPD 自带的甘特图主要面向单个项目，无法方便地从团队成员的角度查看跨项目任务安排。管理人员需要在多个项目之间切换，才能了解每个成员在某个时间段内承担的工作。

因此，需要开发一款独立桌面应用，通过 TAPD Open API 获取多个项目的任务数据，并聚合成统一的团队排期看板。

### 1.2 核心目标

1. 配置多个 TAPD 项目，聚合各项目任务。
2. 以团队成员为一级分组，查看每位成员的跨项目任务。
3. 每个任务独占一行，任务条按照开始日期和结束日期显示。
4. 默认展示当前自然月，支持自定义时间范围。
5. 支持项目、成员、任务状态等条件筛选。
6. 通过项目颜色区分不同项目。
7. 查看任务详情，并能跳转至对应的 TAPD 任务页面。
8. 通过 Tauri 打包为可跨平台运行的桌面应用。

### 1.3 首版不包含的功能

以下功能明确不在首版范围内：

* 不修改 TAPD 任务。
* 不创建、删除或更新任务。
* 不拖拽任务条调整日期。
* 不修改任务负责人、开始日期、结束日期或状态。
* 不维护任务依赖关系。
* 不进行工作量冲突检测或人员负载预警。
* 不提供小时、分钟级时间轴。
* 不提供日、周、月等多种时间轴缩放模式。
* 不实现复杂的项目计划管理、资源调度或排期算法。
* 不将本地数据反向同步到 TAPD。

首版定位是一个**只读的跨项目团队排期视图**，而不是另一个任务管理系统。

## 2. 技术选型

| 模块   | 技术选型                        | 用途                |
| ---- | --------------------------- | ----------------- |
| 桌面容器 | Tauri 2                     | 桌面应用打包与系统能力接入     |
| 前端框架 | Vue 3                       | 页面、组件和交互          |
| 开发语言 | TypeScript                  | 类型约束和数据模型         |
| 构建工具 | Vite                        | 开发服务器与构建          |
| 甘特图  | Frappe Gantt                | 任务条、日期网格及时间轴的基础能力 |
| 状态管理 | Vue Composition API         | 页面状态与筛选状态管理       |
| 数据请求 | 优先采用轻量 HTTP 客户端 | TAPD API 请求       |
| 本地配置 | Tauri 插件或 Rust 命令封装         | 安全保存访问凭据与应用配置     |
| 测试   | Vitest + Vue Test Utils     | 单元测试和组件测试         |

### 2.1 选型约束

1. 使用 Vue 3 + TypeScript，不引入 React。
2. 不引入大型后端服务；首版直接从桌面应用请求 TAPD API。
3. 不依赖需要付费授权才能实现成员分组的甘特图库功能。
4. 优先评估 Frappe Gantt 的源码扩展能力。
5. 若 Frappe Gantt 无法以合理改动成本实现成员分组布局，允许在项目内实现自定义甘特图渲染层，但必须保留清晰的组件边界。
6. 不为了维持原始甘特图库完全不变，而牺牲核心业务需求。

### 2.2 Frappe Gantt 使用策略

Frappe Gantt 作为基础候选库，但不能假定其默认布局直接支持本项目。

必须先验证以下能力：

* 是否可以在任务行之间插入独立的成员标题行。
* 是否可以为每个成员动态插入任意数量的任务行。
* 是否可以根据展开/折叠状态动态改变行数和 SVG 高度。
* 是否可以让日期网格、任务条和左侧行标题保持纵向对齐。
* 是否可以在滚动时保持时间轴和任务条的水平位置一致。
* 是否能够禁止拖拽、调整日期等编辑交互。

如果需要修改第三方库，应将改动限制在独立适配层或项目维护的 fork 中，并记录原库版本及改动原因。

**禁止在未验证布局能力之前，直接围绕 Frappe Gantt 默认任务列表开始开发业务页面。**

## 3. 核心交互与界面设计

### 3.1 页面结构

页面由以下区域组成：

1. 顶部工具栏：应用标题、刷新按钮、最后刷新时间。
2. 筛选区域：时间范围、项目、成员、任务状态。
3. 甘特图区域：左侧分组与任务标题，右侧按日排列的时间轴。
4. 加载、错误、空数据等状态提示。

### 3.2 甘特图布局

甘特图采用成员分组、任务独立成行的结构。

示例：

```text
成员 / 任务                       10/01  10/02  10/03  10/04  10/05
-----------------------------------------------------------------
▼ 张三
  [项目 A] 用户登录改造             █████████
  [项目 B] 订单接口联调                    ███████
  [项目 C] 修复列表分页                          ███
▼ 李四
  [项目 A] 商品页适配                █████████████
  [项目 D] 修复结算问题                      █████
▶ 王五
```

以上仅为结构示意，不代表真实任务日期。

#### 成员分组规则

* 每个成员显示一个独立的分组标题行。
* 成员标题行不显示任务条。
* 成员下的任务按照固定排序规则排列，每个任务独占一行。
* 成员标题行支持展开和折叠。
* 折叠后隐藏该成员的全部任务行。
* 不同成员之间的任务行不混排。
* 成员分组顺序应稳定，避免每次刷新后无规律变化。
* 成员名称缺失或负责人无法匹配的任务，统一归入“未分配成员”分组。

#### 任务行规则

* 每个任务占据一个固定高度的行。
* 任务条的横向位置由开始日期计算。
* 任务条的长度由开始日期和结束日期计算。
* 同一成员在同一天存在多个任务时，显示在不同的任务行上，不进行重叠检测或自动冲突标记。
* 任务标题区域应显示项目标识和任务名称。
* 任务名称过长时截断显示，并提供完整标题提示。
* 点击任务条或任务标题可以查看任务详情。
* 通过独立的“打开 TAPD”操作进入任务原始页面。

### 3.3 时间轴规则

* 时间轴以自然日为最小单位。
* 每一列对应一个自然日。
* 默认时间范围为当前自然月的第一天至最后一天。
* 用户可以通过时间范围筛选控件选择其他起止日期。
* 不提供时间轴缩放按钮。
* 不提供周视图、月视图等不同缩放模式。
* 周末使用轻量视觉区分。
* 当前日期可以使用竖线或背景高亮。
* 任务日期和时间轴均使用统一的本地日期计算规则。

时间范围选择与时间轴缩放是两个不同概念。用户改变筛选范围时，时间轴展示的日期列随之改变，但始终维持日级粒度。

### 3.4 筛选区域

首版包含：

| 筛选项  | 规则               |
| ---- | ---------------- |
| 时间范围 | 默认当前自然月，可自定义起止日期 |
| 项目   | 多选；默认选择所有已启用项目   |
| 成员   | 多选；默认显示全部成员      |
| 任务状态 | 多选；默认显示所有已纳入的状态  |

筛选应作用于已经获取的数据，避免每次切换成员或项目都重新请求 TAPD。

切换筛选条件后，立即更新甘特图。

当筛选后某成员没有任何任务时，默认隐藏该成员分组。是否展示空成员不作为首版必需功能。

### 3.5 项目颜色

* 每个项目具有固定颜色。
* 项目颜色用于任务条或任务条左侧标识。
* 同一项目在不同成员分组下使用相同颜色。
* 颜色分配必须稳定，不得因为任务排序变化而变化。
* 项目颜色应具有足够的视觉区分度。
* 颜色只表达项目归属，不表达任务状态、优先级或风险。

### 3.6 任务详情

点击任务后显示只读详情，至少包含：

* 任务名称
* 所属项目
* 负责人
* 任务状态
* 开始日期
* 截止日期
* TAPD 任务链接

可根据 TAPD API 实际可用字段补充优先级、任务描述等信息，但不得为了补齐展示字段而假造数据。

## 4. 数据接入与安全设计

### 4.1 TAPD 数据访问

使用 TAPD Open API 和用户提供的 `personal_token` 获取数据。

在开始正式开发之前，必须确认当前 TAPD 账号、Token 权限和实际 API 能力，包括：

* 能否读取配置项目中的任务。
* 是否需要逐个项目查询任务。
* 如何获取项目列表及项目标识。
* 如何查询任务的负责人、状态、开始日期和截止日期。
* 如何获取任务详情及原始任务链接。
* 是否存在分页、限流和字段权限限制。
* API 的认证方式、响应格式和错误码。

不得凭经验臆造 TAPD API 地址、参数名称、响应字段或分页规则。

如果某项能力在 API 文档或真实响应中无法确认，应先记录阻塞项并进行验证，再实现相应功能。

### 4.2 多项目数据获取

项目列表作为独立配置维护。

每个项目至少包含：

```ts
interface ProjectConfig {
  id: string;
  name: string;
  enabled: boolean;
  color: string;
}
```

项目 ID 应使用 TAPD 的实际项目标识，并与任务响应中的项目标识保持一致。

数据获取建议采用以下流程：

1. 读取启用的项目列表。
2. 并发或分批请求各项目任务。
3. 处理分页，直到满足 API 定义的查询条件。
4. 将各项目结果转换为统一任务模型。
5. 去重并规范化日期、状态、成员等字段。
6. 应用当前筛选条件。
7. 将结果传入甘特图渲染层。
8. 显示刷新时间和数据加载结果。

并发请求应设置合理上限，避免一次刷新同时请求所有页面和项目而触发限流。

如果某个项目请求失败，应保留其他项目已成功获取的数据，并明确显示失败项目及错误原因；不得把部分成功结果伪装成全部项目加载成功。

### 4.3 凭据安全

* 不得将 `personal_token` 硬编码到源代码、配置文件、测试样例或日志中。
* 不得将 Token 写入版本控制。
* 不得将 Token 放入 URL 查询参数。
* 不得在错误日志中输出完整 Token。
* 不得把 Token 保存到普通 `localStorage`。
* 优先使用操作系统凭据存储能力，通过 Tauri 插件或 Rust 命令封装读写。
* 前端仅在请求确有需要时使用凭据，不向无关组件传递。
* 提供清除凭据的能力。
* 配置文件只保存非敏感配置，例如项目列表、颜色和筛选偏好。

如果最终采用的 TAPD 认证方式需要额外处理，应先核实其认证规范，再决定请求应由前端还是 Tauri 后端执行。

### 4.4 刷新与错误处理

首版提供手动刷新。

刷新过程中：

* 显示加载状态。
* 禁止重复触发相同的刷新操作。
* 成功后更新任务数据和最后刷新时间。
* 失败时显示可理解的错误提示。
* 不因单个项目失败而丢弃其他成功项目的数据。

首版不要求后台定时刷新、复杂缓存系统或离线数据同步。

## 5. 统一数据模型

业务层不能直接依赖 TAPD 原始响应结构。应建立 TAPD 适配层，将原始数据转换为统一模型。

### 5.1 任务模型

```ts
export interface ScheduleTask {
  id: string;
  title: string;

  projectId: string;
  projectName: string;
  projectColor: string;

  assigneeId: string | null;
  assigneeName: string;

  startDate: string | null;
  dueDate: string | null;

  status: string;
  priority?: string;

  tapdUrl: string;

  rawStatus?: string;
}
```

日期格式统一为 `YYYY-MM-DD`，并且应作为自然日处理，避免无意义的时区转换造成日期偏移。

字段映射必须根据实际 TAPD 响应确定。

### 5.2 日期缺失规则

不得自行推算或虚构任务开始日期、截止日期。

处理规则：

1. 开始日期和截止日期均存在：按完整区间显示。
2. 只有截止日期：将任务放入“未排期任务”区域，或使用单日标记展示；首版不得将截止日期误认为任务真实开始日期。
3. 只有开始日期：显示单日标记或归入未排期区域，具体方案由 PoC 确认。
4. 两个日期都不存在：归入未排期任务列表，不在日历上生成虚构任务条。
5. 开始日期晚于截止日期：标记为异常数据，不得自动交换日期并静默隐藏问题。

对于只有单日日期的任务，若采用单日标记展示，必须在视觉上与有明确起止日期的区间任务区分。

“未排期任务”属于辅助区域，不应破坏成员分组和日级时间轴的布局。

### 5.3 成员与项目去重

* 成员优先通过稳定的 TAPD 用户标识关联，不以显示名称作为唯一标识。
* 同名用户不能直接合并。
* 项目优先通过 TAPD 项目标识关联，不以项目名称作为唯一标识。
* 同一任务因分页、重复请求等原因重复出现时，应根据稳定任务 ID 去重。
* 任务负责人缺失时统一映射到“未分配成员”。

## 7. 甘特图渲染设计

这是本项目最关键的技术模块。

### 7.1 核心布局原则

**成员标题行、任务行、日期网格和任务条必须共享统一的布局计算结果。**

禁止分别在不同组件内独立计算纵向坐标，导致成员标题、任务名称和任务条错位。

建议使用以下基础参数：

```ts
export interface GanttLayoutConfig {
  headerHeight: number;
  memberRowHeight: number;
  taskRowHeight: number;
  dayColumnWidth: number;
  labelColumnWidth: number;
}
```

具体像素值由界面设计和 PoC 确定，不在业务逻辑中散落硬编码。

### 7.2 布局模型

```ts
export type GanttRow =
  | {
      type: 'member';
      key: string;
      memberId: string;
      memberName: string;
      y: number;
      height: number;
    }
  | {
      type: 'task';
      key: string;
      taskId: string;
      memberId: string;
      y: number;
      height: number;
    };
```

布局计算负责：

* 按成员分组。
* 按确定的规则对组内任务排序。
* 插入成员标题行。
* 根据折叠状态决定是否生成任务行。
* 计算每一行的 `y` 坐标和高度。
* 计算时间轴起始日期、结束日期及日列位置。
* 计算任务条的 `x` 坐标、宽度和 `y` 坐标。
* 计算画布总高度和总宽度。

布局模型是唯一的几何数据来源。

### 7.3 日期坐标计算

假设：

* `rangeStart`：时间轴第一天。
* `dayColumnWidth`：每个自然日的列宽。
* `taskStart`：任务开始日期。
* `taskEnd`：任务结束日期。

对于日期 `d`，其横坐标为：

```text
x(d) = dateDiffInDays(rangeStart, d) × dayColumnWidth
```

区间任务的宽度按照自然日区间计算：

```text
width = (dateDiffInDays(taskStart, taskEnd) + 1) × dayColumnWidth
```

以上为布局计算的基础定义。实际绘制时可以设置条形内边距，但不得改变区间所覆盖的日期。

任务跨越时间轴边界时，应按当前可视范围裁剪任务条，不改变原始任务日期。

### 7.4 纵坐标计算

* 成员标题行占据独立高度。
* 成员下方任务依次排列。
* 任务行高度固定。
* 折叠成员后，重新计算其后的所有行位置。
* 任务条的 `y` 坐标必须与对应任务标题行完全一致。
* 行高、总画布高度、滚动容器尺寸必须在同一轮布局计算中更新。

不得通过为不同成员手工设置 SVG 偏移量的方式实现分组。

### 7.5 横向与纵向滚动

界面需要支持多个日期列及大量任务行。

建议：

* 左侧任务名称列保持固定。
* 右侧日期区域支持横向滚动。
* 任务名称列与日期区域保持纵向对齐。
* 日期表头在纵向滚动时保持可见。
* 成员折叠、展开后，正确更新总高度。
* 横向滚动时，日期表头、背景网格与任务条保持一致。

如果左右区域采用独立滚动容器，必须显式同步纵向滚动位置，避免出现滚动偏差。

### 7.6 Frappe Gantt 适配要求

先实现一个最小可行的渲染验证，不要立即接入全部业务数据。

验证数据至少包含：

* 2 个成员。
* 每个成员 3 个以上任务。
* 不同项目颜色。
* 同一成员的多个任务日期重叠。
* 跨越多天的任务。
* 不同成员的任务数量不一致。
* 一个折叠成员。

PoC 必须验证成员标题行、独立任务行、日期网格、折叠展开和滚动对齐。

如果原库的数据结构与本项目的行结构冲突，可以选择：

1. 维护一层 Frappe Gantt 自定义适配器。
2. 基于固定版本维护最小化 fork。
3. 在项目内编写独立 SVG 甘特图渲染组件。

采用哪种方式，应根据 PoC 的实际改动范围决定。不得为了使用现有库而引入大量脆弱的 DOM 操作或 CSS 补丁。

## 8. 状态管理与性能

### 8.1 状态划分

至少区分：

* 项目配置。
* 原始任务数据。
* 规范化任务数据。
* 当前筛选条件。
* 成员折叠状态。
* 当前选中的任务。
* 加载状态。
* 错误状态。
* 最后成功刷新时间。

筛选状态、折叠状态和当前选中任务属于界面状态，不应混入 TAPD 原始数据模型。

### 8.2 性能要求

首版主要面向约 10 个项目的团队级任务数据。

必须做到：

* 对项目请求进行合理的并发控制。
* 避免筛选时重新请求所有 TAPD 项目。
* 避免每次筛选都重复进行不必要的全量数据映射。
* 将分组、筛选和布局计算与视图组件分离。
* 仅在数据、筛选、折叠状态或时间范围变化时重新计算布局。
* 不在渲染循环中重复解析日期字符串。
* 大量任务时不得出现明显的滚动卡顿。

首版暂不要求虚拟滚动。应先根据实际数据量和性能测试结果判断是否需要实现。

## 9. 异常与边界情况

必须覆盖以下情况：

1. Token 未配置。
2. Token 无效或失效。
3. TAPD API 网络错误。
4. 某个项目请求失败，其他项目请求成功。
5. 项目没有任务。
6. 筛选后没有匹配任务。
7. 任务负责人为空。
8. 任务开始日期缺失。
9. 任务截止日期缺失。
10. 任务日期格式异常。
11. 任务开始日期晚于截止日期。
12. 任务跨越当前时间轴范围。
13. 同一任务重复返回。
14. 同名成员具有不同用户 ID。
15. 同一天存在多个任务。
16. 成员任务数量差异较大。
17. 成员折叠后再刷新数据。
18. 刷新过程中发生错误。

对异常数据应尽量保留原始任务信息，并明确展示或记录问题；不得通过静默修改业务字段掩盖数据异常。

## 13. Codex 执行约束

执行本方案时必须遵守以下规则：

1. **先检查项目，再修改项目。** 先读取仓库结构、现有开发规范、依赖、构建命令和相关文档，不要假定这是一个空仓库。
2. 如果仓库已有技术选型或项目规范，应先判断是否与本方案冲突；未经说明不得大规模重构现有工程。
3. 第一阶段先完成 PoC 和技术验证，再实现完整功能。
4. 如果需要修改 Frappe Gantt 源码，应记录修改点、原因和升级影响。
5. 不得虚构 TAPD API 地址、参数、字段、响应结构或认证方式。应以官方文档和真实响应为依据。
6. 如果 TAPD API 权限、日期字段或成员标识存在无法确认的问题，应先输出阻塞项和验证方法，不得猜测后继续实现。
7. 不得在代码、测试数据、日志或文档中提交真实 Token。
8. 不得自行添加任务编辑、拖拽改期、写回 TAPD、冲突检测、时间轴缩放等范围外功能。
9. 业务数据映射、筛选、日期计算、分组和布局计算应保持可测试、可独立维护。
10. 每个阶段结束时运行相关测试和构建命令，并报告实际执行结果。
11. 不得声称未实际执行的测试已通过，也不得把未验证的 API 行为描述为已验证。
12. 优先采用小步提交式开发；每次改动保持目标明确，不进行无关重构。
13. 如果实际实现与本方案出现冲突，先说明冲突、影响和建议方案，再决定是否调整设计。
