# TeamSight MCP 场景与能力职责梳理

日期：2026-11-02。

状态：需求讨论稿 v0.1。

本文整理本轮对话中的目标、已确认业务规则，以及建议的能力分工。已确认规则作为后续设计依据；能力分组、结果组织方式和流程衔接属于本次提出的设计建议。本文描述目标需求，具体工具名称、接口参数和当前实现覆盖情况在后续设计中确定。

## 1. 产品目标

用户在对话中提出工作目标，Agent 按 skills 组织工作，通过 TeamSight MCP 获取 TAPD 数据、完成计算、操作任务，并在需要交互时打开 MCP Apps。

TeamSight 的核心组成如下：

| 组成 | 职责 |
| --- | --- |
| MCP 配置管理 | 保存凭据、项目、成员、分组、工时和日历等配置 |
| MCP 基础 TAPD 能力 | 向 Agent 暴露有明确输入和结果的部分 TAPD 接口 |
| MCP 场景数据与计算能力 | 封装重复取数、关联、汇总、工时计算、容量计算和排期计算 |
| MCP Apps | 渲染配置表单、任务与工时甘特图及相关详情 |
| Skills | 规定场景中的处理步骤、判断方法、排期偏好和输出要求 |
| Agent 与宿主工具 | 理解需求、组合上述能力、解释结果，并在代码仓库中完成开发等工作 |

目标运行环境为 macOS、Windows；Linux 后续支持。目标宿主先覆盖 Codex，DeepSeek Harness 后续支持。平台运行、工具调用、Apps 渲染和 skills 使用分别验收。

## 2. 已确认的业务规则

### 2.1 配置、身份和默认范围

| 项目 | 已确认规则 |
| --- | --- |
| 个人令牌 | 未配置 personal_token 时，调用业务能力应引导用户在会话内的 MCP Apps 配置页填写；用户也可以通过对话主动打开配置页 |
| 当前用户 | “我”和未指定负责人的普通任务，使用 personal_token 对应用户 |
| 项目同步 | 配置令牌后自动获取、保存用户有权限的项目，全部默认启用 |
| 项目管理 | 支持启用／禁用、别名、排序和颜色 |
| 成员发现 | 先匹配本地身份，没有匹配项时通过 TAPD 成员目录获取候选；确定成员后保存身份 |
| 首次保存成员 | 只保存身份，默认团队范围另行指定；当次工作完成后的答复末尾可以提示是否分组 |
| 成员管理 | 支持分组、启用／禁用、排序、添加和删除 |
| 分组关系 | 一个成员可以属于多个分组，只配置一个默认分组 |
| 默认团队 | 未明确指定成员或分组的团队类请求，采用默认分组；显式指定范围时采用指定范围 |
| 分组去重 | 多分组查询按稳定成员身份去重，任务及工时避免重复统计 |
| 单用户范围 | 当前按一个用户使用本人令牌设计，更换用户令牌的场景暂不考虑 |

测试人员身份可以来自当前对话或成员分组。保存成员身份、成员所属分组、默认团队范围是三个不同概念。

### 2.2 工时与每日容量

1. 每日规定工时默认 8h，允许修改，并作为排期容量依据。
2. 支持启用／禁用中国节假日及调休；工作日、请假等已有工时规则继续纳入每日有效目标。
3. 已过去日期，用当日实际花费工时判断达标。
4. 当天及未来日期，用当日实际花费与分配到当日的剩余工时之和判断达标。
5. 任务剩余工时按预估减去截至计算日的累计花费计算，最低为 0；每日预计工时由任务剩余量分配得到。
6. 用于判断的每日工时小于当日有效规定工时时，视为不达标。
7. 没有预估工时，计算时按预估 0 处理。
8. 没有开始和结束日期，或仅有其中一个日期，均按未排期处理。
9. 缺预估、未排期的任务，只要有花费记录，就按花费日期和填报人参与实际工时统计及展示。
10. 有预估但未排期的任务保留其剩余工作量，排期后再将剩余量分配到具体日期。

实际工时读取与任务排期窗口分开处理，避免遗漏未排期任务或排期不在展示窗口内的花费。字段缺失的上述处理规则，与接口失败、分页不完整等取数问题分别表达。

用户当前的估时习惯是在实际工作量基础上预留约 50%，应对突发情况和团队管理工作。具体估时方法在 skills 阶段细化；MCP 使用任务最终填写的预估参与计算，避免重复叠加余量。

### 2.3 普通需求的拆解与排期

- 通常以 TAPD 链接作为需求入口，在对话中说明拆解范围，例如前端或后端。
- 未指定负责人时使用当前用户；指定负责人时匹配对应 TAPD 用户。
- 仅拆分任务及预估工时：创建关联原需求的 TAPD 任务，日期留空。
- 拆解时同时排期：结合负责人已有安排、每日容量及协作依赖，创建带排期的任务。
- 后续补排期：读取已创建任务及相关协作任务的最新安排，在原任务上补充排期。
- 后续排期既可以在原对话继续，也可以在新会话中通过 TAPD 链接发起。
- 普通排期区分具体交付依赖，例如接口就绪、联调、提测；前端任务可以紧挨联调任务，从后向前安排。
- 协作关系结合用户在对话中的明确指定与 Agent 对需求、任务内容的识别。

### 2.4 排期的连续性偏好

允许利用每天剩余的零散工时。优先保证单个任务执行的完整性和连续性，同需求的不同任务允许间隔，条件相近时尽量靠近。

| 任务拆解与可用时间 | 排期偏好 |
| --- | --- |
| 两个 4h 任务，周一、周三各空余 4h | 可以分别安排，中间允许有间隔 |
| 两个任务分别 2h、6h，周一空余 2h、周三空余 6h | 可以分别安排，每个任务在当天完整完成 |
| 两个任务分别 2h、6h，需要打散其中的任务才能填入零散日期 | 倾向寻找一天或连续工作日内完成的安排 |
| 一个 8h 任务 | 倾向一天完成，或在连续两个工作日内完成 |

这些是排期偏好。候选安排还需满足明确的日期约束、负责人可用容量及协作依赖。具体候选排序方式在后续设计中明确。

### 2.5 紧急需求分析

- 紧急需求仅做分析，任务创建、负责人变更和已有排期移动均作为模拟结果呈现。
- 先分析单人直接承接，再分析调整已有排期的空间；单人无法满足时，再评估多人协作。
- 测试任务满足任一条件即可识别：名称包含“测试”；处理人被当前对话或成员分组认定为测试人员。
- 研发任务与测试任务通常关联同一条 TAPD 需求。
- 判断已有研发任务是否可以调整时，以关联需求中时间最早的已排期测试任务作为边界。
- 没有测试排期时，该需求内任务可以作为可调整候选；同时检查已知 deadline 和其他协作约束。
- 多人协作需要结合功能相关度、独立性和依赖判断，人员容量分别计算。

### 2.6 甘特图

| 模式 | 正常显示、可交互的前景 | 半透明淡化、不可交互的背景 |
| --- | --- | --- |
| 任务优先，默认 | 任务排期及完成情况 | 每日工时情况 |
| 工时优先 | 每日工时情况 | 任务排期及完成情况 |

两种模式共用成员、日期和计算结果，调整任务层与工时层的前后顺序及交互对象。每日工时在对应日期的纵向区域内呈现。

交互范围为点击、悬浮、筛选和查看详情。任务拖拽及通过甘特图直接修改排期不在本次交互范围内。

## 3. 建议的职责边界

| 工作 | MCP | Skills 与 Agent | MCP Apps |
| --- | --- | --- | --- |
| 需求读取 | 提供正文、附件及关联对象的可获取内容与引用 | 理解功能、验收要求，识别缺口 | 按需展示结构化内容 |
| 任务拆解 | 提供需求上下文和任务创建能力 | 确定拆解范围、边界、描述及依赖 | 按需查看任务清单 |
| 工时预估 | 读取和保存最终预估值 | 决定估时方法、假设与余量 | 展示预估及依据 |
| 工时统计 | 统一计算实际、剩余、每日分配及差额 | 组织查询，解释结果 | 展示工时及贡献明细 |
| 排期 | 读取已有安排，计算容量、生成候选并校验约束 | 识别依赖、明确偏好，比较和选用候选 | 查看候选安排和任务详情 |
| 任务操作 | 创建、更新、读回，返回逐项结果 | 将用户意图转成任务操作，处理后续流程 | 展示结果或操作状态 |
| 报告 | 提供对应期间的工作事实和来源 | 按场景组织日报、周报、月报 | 按需查看相关明细 |
| 风险分析 | 提供排期、容量、依赖和可复查的计算事实 | 按后续确定的方法识别、解释和排序风险 | 展示风险关联对象及依据 |
| 紧急插单 | 按候选任务、人员、约束计算可行安排及影响 | 估时、判断可拆分性、组织单人及多人分析 | 对比模拟安排与当前安排 |
| 代码实现 | 提供任务及需求上下文 | 宿主 Agent 结合代码仓库完成开发和验证 | 提供任务参考信息 |

数值计算和约束校验采用统一实现。自然语言理解、场景流程和报告文案由 skills 指导 Agent 完成。

场景封装围绕可复用的数据结果组织，例如需求上下文、成员期间工作事实、每日容量、协作关系和候选排期。一个结果可以供多个 skills 复用。

## 4. 使用场景与能力对应

| 场景 | MCP 提供的能力和结果 | Skills 与 Agent 的工作 | 最终结果及 TAPD 操作 |
| --- | --- | --- | --- |
| 读取今日任务并实现 | 当前用户、相关任务、需求上下文、协作信息 | 理解要求、选择任务、结合仓库实现和验证 | 开发结果；TAPD 状态更新按当次请求处理 |
| 需求仅拆解、估时 | 需求上下文、已有子任务、负责人身份、任务创建与读回 | 按指定前端／后端范围拆解，编写描述、估时 | 创建未排期任务，返回逐项结果与链接 |
| 需求拆解并排期 | 上述能力，加每日容量、依赖和候选排期计算 | 形成任务及约束，按偏好选用候选 | 创建带排期任务 |
| 已有任务补排期 | 链接定位、已有任务、相关协作排期、候选计算、任务更新 | 识别交付节点，选择安排，组织更新 | 更新原任务排期并返回结果 |
| 个人周报 | 指定期间的个人工作项、花费和可获取的期间活动 | 按后续报告 skill 汇总和表达 | 个人周报；文本格式后续细化 |
| 团队周报／月报 | 默认组或指定范围的期间工作事实，按身份去重 | 按后续报告 skill 组织团队结果 | 团队报告 |
| 个人／团队工时预警 | 每日目标、实际、预计、差额、贡献与未排期剩余量 | 组织查询和说明，提示关注项 | 工时结论及可追溯明细 |
| 团队甘特图 | 指定日期范围的任务安排、完成状态和每日工时 | 明确范围，调用展示能力并解读 | 可切换任务／工时优先的交互图 |
| 团队进度风险 | 排期、剩余量、每日容量、协作节点及事实依据 | 按后续风险 skill 判断和解释 | 风险分析及关联对象 |
| 紧急需求：单人 | 团队容量、已有任务及其需求、最早测试边界、模拟调整结果 | 估时，比较直接承接与调整后承接 | 可行成员、日期、受影响任务和依据；仅分析 |
| 紧急需求：多人 | 上述能力，加多任务依赖与多人候选计算 | 判断功能是否适合拆分，明确协作和交接 | 分工候选、时间安排和影响；仅分析 |

个人与团队查询复用同类数据能力，通过成员范围区分。团队报告与工时统计的默认范围采用默认分组；依赖分析可以补齐默认组之外的相关协作任务。

## 5. 建议的 MCP 能力分组

以下是逻辑分组，用于讨论数据和计算边界，具体工具数量与命名后续确定。

### 5.1 配置与身份

- 检查凭据及业务配置状态，打开设置 Apps。
- 读取当前用户身份，支持“我”和默认负责人解析。
- 同步、管理项目，保留成员目录和已识别身份。
- 管理成员多分组、默认分组、启用状态及展示顺序。
- 管理每日规定工时、日历开关及沿用的工时配置。

涉及凭据的填写通过配置表单完成；业务查询返回配置状态和必要的身份信息。

### 5.2 基础 TAPD 接口

- 获取项目、成员目录、字段和状态等元数据。
- 搜索及读取需求、任务、缺陷等场景所需工作项。
- 读取工时记录。
- 创建任务，更新任务描述、负责人、预估和排期等所需字段。
- 提供分页和查询范围信息，统一必要的输入校验和结果表达。

基础接口的首批范围由本次场景反推，并通过 TAPD 文档及实际权限验证。需求读取材料、历史记录和关联关系的获取能力也在此范围核实。

### 5.3 需求与期间工作上下文

- 根据 TAPD 链接或对象身份定位需求、任务及所属项目。
- 聚合需求材料、已有子任务、负责人、状态、估时和排期。
- 提供指定成员、项目、期间的任务及花费事实。
- 补齐与目标需求相关的协作任务和测试任务。
- 对可获取的期间活动给出来源，区分当前状态和期间发生的事实。

该分组承担重复取数和关联。需求内容的理解、任务拆分和报告写作由 Agent 完成。

### 5.4 工时与容量

- 按日期、填报人统计实际花费。
- 按任务读取累计花费，计算剩余量。
- 按既定规则生成每日预计分配、目标和差额。
- 输出未排期任务及其剩余工作量。
- 计算已有安排下的每日可用容量。
- 保留工时贡献明细、查询范围、来源时间和取数完整性。

为已有任务重新排期时，容量计算需要识别本次目标任务与其他任务的占用，避免重复扣除目标任务的原有预计分配。实际花费保留为已经发生的事实。

### 5.5 协作与约束上下文

- 关联研发任务、协作任务、联调节点和测试任务。
- 记录依赖的交付内容、相关对象及来源。
- 区分用户明确指定的关系与 Agent 推断的关系。
- 获取同需求最早已排期测试任务及其日期，供紧急分析使用。
- 为后续会话提供已保存、仍有效的依赖说明，并结合 TAPD 最新状态使用。

测试人员身份、测试关键词和对话识别结果作为输入依据。存在重要关联缺口时，结果中保留待补充的信息。

### 5.6 排期计算与模拟

输入包括待安排任务、负责人、工时、已有占用、可排日期、协作节点和排期偏好。

输出包括：

- 任务起止日期及每日分配工时。
- 已满足的约束、剩余冲突及无法安排的部分。
- 与协作、联调、测试节点的关系。
- 紧急分析中需要移动的已有任务及其影响。
- 候选之间在完成时间、单任务连续性和同需求集中程度上的差异。

普通排期支持从起始节点顺排，以及以联调等节点为锚点向前倒排。紧急分析在候选中模拟已有任务移动和多人分工。

计算与 TAPD 写入分别提供，保证同一计算能力可以用于普通需求落地及紧急需求分析。

### 5.7 任务操作与执行结果

- 根据拆解结果创建关联原需求的任务。
- 根据选用的安排更新已有任务。
- 返回每项操作的目标对象、结果及 TAPD 链接。
- 支持识别重复请求，并在部分成功时继续处理未完成项。
- 执行后读取实际结果，供 Agent 核对和说明。

普通需求的任务创建与更新由对应工作流组织；紧急需求工作流使用读取和模拟结果。

### 5.8 Apps 渲染

- 打开配置表单。
- 基于指定范围及计算结果打开甘特图。
- 切换任务优先／工时优先，调整前景、背景与交互层。
- 展示任务详情、每日工时构成及相关需求链接。
- 支持成员、项目、日期等经确认的筛选方式。

数据与计算工具返回可供 Agent 使用的结构化结果。渲染能力使用同一结果，避免 Agent 解读与图中展示采用不同来源。

## 6. 建议的 skills 组织

| Skill 方向 | 负责指导的内容 | 本轮确定程度 |
| --- | --- | --- |
| 需求读取 | 如何阅读需求、提取范围和验收要求、发现缺口、识别协作 | 方向已确定，具体方法后续细化 |
| 任务拆解 | 前端／后端等指定范围的拆分方式、任务描述和完成标准 | 创建任务及两种排期时机已确定，拆分方法后续细化 |
| 工时评估 | 估时依据、假设、余量和调整方式 | 当前约 50% 余量作为背景，算法后续深入讨论 |
| 任务排期与分配 | 默认负责人、协作关系、联调回排、任务连续性偏好 | 核心偏好已确定，候选比较细节后续细化 |
| 工时预警 | 如何选择期间、检查差额、说明实际与预计口径 | 核心数值规则已确定，表达方式后续细化 |
| 日报／周报／月报 | 内容范围、读者、模板、事实组织和输出格式 | 明确留到 skills 阶段深入讨论 |
| 进度风险 | 风险类型、判断方法、程度和建议表达 | 明确留到 skills 阶段深入讨论 |
| 紧急需求评估 | 单人、移动已有任务、多人拆分的分析顺序和决策依据 | 仅分析及最早测试边界已确定，语义判断方法后续细化 |
| 今日任务实施 | 如何从任务进入需求理解、仓库实现及验证 | MCP 提供上下文，开发流程结合宿主及仓库规则 |

上述为能力方向，可以通过公共指导和场景流程复用，最终 skill 的数量及包装方式后续确定。

## 7. 三条主要工作链路

### 7.1 普通需求：仅拆解与估时

1. 用户提供 TAPD 链接，指定前端或后端等拆解范围。
2. MCP 获取需求、已有任务、当前用户或指定负责人等上下文。
3. Agent 按对应 skills 理解需求、拆分任务、编写描述和预估。
4. MCP 创建关联需求的任务，日期留空，返回逐项结果。
5. Agent 汇总已创建任务、链接及需继续处理的事项。

对话本身已明确的创建意图作为流程依据，具体任务清单的展示和调整方式在 skills 中组织。

### 7.2 普通需求：后续补排期

1. 用户在原会话继续，或在新会话提供 TAPD 链接并要求排期。
2. MCP 读取已有任务、负责人占用、协作任务安排及已保存的依赖信息。
3. Agent 明确本次相关交付节点和约束，形成用于计算的输入。
4. MCP 生成候选安排，支持紧挨联调节点向前倒排。
5. Agent 按排期偏好组织选用结果，MCP 更新原任务并返回实际结果。

任务存在于 TAPD，必要依赖关联到需求或任务，原聊天记录作为可用补充。新会话可以从对象链接重新进入流程。

### 7.3 紧急需求：仅分析

1. 用户提供需求、deadline 和需要分析的人员范围；团队范围省略时采用默认分组。
2. Agent 理解需求并形成待评估任务、估时和依赖。
3. MCP 获取团队容量及相关安排，先计算单人直接承接候选。
4. 需要调整已有排期时，补齐受影响需求及最早测试边界，计算可移动空间。
5. 单人无法满足时，Agent 判断适合多人协作的拆分方式，MCP 计算对应候选。
6. Agent 输出可行性、人员安排、受影响任务、依据及待定项；Apps 按需展示模拟结果。

## 8. 结果组织建议

| 结果 | 应包含的信息 |
| --- | --- |
| 查询上下文 | 项目与成员范围、业务日期、计算日、来源时间、数据完整性 |
| 需求与任务事实 | TAPD 对象身份及链接、原始字段、负责人、关联关系 |
| 工时结果 | 每日目标、实际、分配的剩余量、合计、差额、任务贡献、未排期剩余量 |
| 协作关系 | 前后置对象、交付节点、用户指定或推断来源、待定信息 |
| 排期候选 | 逐任务日期和每日工时、约束满足情况、受影响对象及差异 |
| 执行结果 | 逐任务成功／失败状态、实际对象链接、已经完成和仍待处理的事项 |

建议保留原始预估字段及用于计算的有效值：缺预估时有效值为 0，原始缺失状态仍可追溯。部分日期也保留原始信息，在排期计算和展示中统一标记为未排期。

任务优先详情重点展示需求关联、负责人、状态、排期和工时；工时优先详情重点展示当天实际、预计分配、目标、差额及贡献任务。字段和视觉细节在界面设计时细化。

## 9. 后续细化与验证事项

### 9.1 已明确留到 skills 阶段的内容

- 工时评估方法，以及约 50% 余量在不同任务中的使用方式。
- 日报、周报和月报的统计范围、内容组织及模板。
- 进度风险分类、判断方法及表达。
- 拆解粒度、任务描述模板、候选排期比较和重要推断的沟通方式。

### 9.2 本次提出、尚待后续确定的设计建议

- 项目再次同步时保留用户已修改的启用状态、别名、颜色和排序，新发现项目默认启用。
- 首次配置完成后恢复被配置阻断的原请求。
- 依赖与交付节点的具体存储位置、修订及失效方式。
- 场景数据结果的复用、来源标识，以及 Apps 中选择内容如何供后续对话使用。

### 9.3 技术设计需要验证的能力

- TAPD 链接类型、对象定位、当前用户身份和项目枚举的实际覆盖范围。
- 需求正文、图片、附件、关联任务和期间活动的接口可获取程度。
- 各项目成员、工作流状态、工时单位、任务必填字段和实际读写权限。
- 缺日期任务与独立工时记录的取数方式、分页完整性和关联补齐。
- 目标平台上的运行、安装、配置和持久化行为。
- 各目标宿主对工具、MCP Apps 和 skills 的支持及实际交互。

这些事项为后续设计和验证输入，不能据此认定对应能力已经实现或验收。
