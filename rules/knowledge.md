# Knowledge Rules

## When To Update Knowledge

任务完成后，如果出现以下情况，Agent 应直接更新根目录下正式 `knowledge`：

- 现有 `knowledge` 缺失，且本次任务验证出了稳定事实。
- 现有 `knowledge` 与源码、配置、Swagger 或用户明确指令不一致，需要修正。
- 本次任务总结出了可复用的实现模式、路径映射、工具用法或禁止项。
- 本次任务发现了现有知识中的遗漏、错误或过时信息。
- 该信息未来大概率会被重复使用，具有长期沉淀价值。

## When Not To Update Knowledge

以下情况不更新正式 `knowledge`：

- 单次任务的临时结论。
- 未经验证的猜测或推断。
- 只对当前文件有效的局部细节。
- 用户没有确认，且无法从源码、配置或真实工具输出验证的业务判断。
- 与现有知识重复，且没有提供新的有效信息。
- 信息时效性较短，不适合作为长期知识保存。

## Knowledge Update Rules

当 Agent 判断需要沉淀知识时，必须遵循以下规则：

1. 直接在根目录下正式 `knowledge` 中创建或更新对应知识文件。
2. 更新前先检查现有知识，避免重复创建相同主题的文件。
3. 优先更新已有知识文件；只有在知识主题独立、现有文件不适合承载时，才创建新文件。
4. 更新时应保留已有有效内容，不得因新增知识而覆盖或丢失无关信息。
5. 新增内容应明确区分已验证事实、适用条件、限制和注意事项。
6. 对于来自源码、配置、Swagger 或工具输出的信息，应以实际验证结果为准。
7. 如果发现现有知识与当前真实情况不一致，应修正过时或错误的内容，而不是简单追加新结论。
8. 保持知识文件结构清晰，避免重复、冗余和碎片化。

## Knowledge Update Restrictions

- Agent 可以自主判断是否需要更新知识，但必须遵守上述创建条件和排除条件。
- 只有具备足够验证依据的信息，才能写入正式 `knowledge`。
- 不得将猜测、临时解决方案或未经确认的业务判断作为确定事实写入知识库。
- 不得为了记录每次任务的执行过程而更新知识。
- 不得仅因为任务完成、测试通过或发现某个问题，就强制产生知识更新。
- 如果无法确定某项信息是否具有长期价值或缺乏必要的验证依据，应放弃更新，而不是勉强沉淀。

## Knowledge Update Reporting

如果本次任务更新了正式 `knowledge`，必须在最终回复中说明：

1. **更新文件**：列出新增或修改的知识文件路径。
2. **更新内容**：简要说明沉淀或修正了哪些知识。
3. **更新依据**：说明相关信息通过什么方式得到验证。
4. **待确认事项**：如果仍存在需要用户确认的业务判断或不确定信息，必须明确指出；没有则无需说明。

如果本次任务没有产生值得沉淀的知识，无需在最终回复中专门说明知识更新情况。

## Knowledge Consistency

- 正式 `knowledge` 应尽可能反映当前项目真实、有效的技术和业务事实。
- 当后续任务发现已有知识过时或错误时，应及时修正。
- 当源码、配置、Swagger 与知识文档存在冲突时，应优先核实真实情况，并根据权威来源更新知识。
- 如果不同来源之间存在无法解决的冲突，不得自行选择一个结论写入知识，应向用户说明冲突并请求确认。
